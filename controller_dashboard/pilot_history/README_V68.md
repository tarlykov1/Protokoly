# v6.8 – диагностический этап перед подключением текущих данных Битрикс24

**Источник истины и история:** ветка `feature/controller-dashboard`, PR #60 в `tarlykov1/Protokoly`.

Работающая v6.7 остаётся без изменений. Новый модуль `live_probe_v68.py` **не подключён к FastAPI** и не предоставляет пользователям никаких новых API-маршрутов. Это намеренно: статический тестовый токен сам по себе не подтверждает доступ контролёра к группам и поручениям.

## Назначение

Один диагностический запрос `tasks.task.list` (REST v2) к одной **явно разрешённой** рабочей группе. Читается только первая страница (до 50 задач); печатаются агрегаты кодов статуса, число заполненных сроков, признак возможного продолжения. Названия задач, тексты комментариев, ID сотрудников и конкретные ID задач не выводятся. Никакие данные не записываются, история SQLite не изменяется, расписание фоновой синхронизации отсутствует.

Команда на сервере, только после назначения тестовой группы и проверки прав интеграции:

```bash
cd /webapp/app
CONTROLLER_PILOT_ALLOWED_GROUPS='123' PYTHONDONTWRITEBYTECODE=1 python3 -B /tmp/controller_timeline_v6_8_probe/probe_cli_v68.py --group-id 123
```

`123` – **пример**, не фактическая группа Битрикс24. Запустить тест можно только после замены на существующий ID, выделенный для пилота. При несовпадении ответа с запрошенной группой модуль прекращает обработку.

**Важное ограничение:** доступ интеграционного пользователя не равен доступу конкретного контролёра. До включения реальных задач в веб-кабинет требуются серверная авторизация по пользователю, проверка состава и прав его групп Битрикс24, HTTPS и согласование списка групп.

## Дальнейшая интеграция – после диагностики

1. Подтвердить совместимость существующего `fast_bitrix` и REST v2, схему ответов для одной группы и допустимую нагрузку.
2. Получить подтверждённые текущие статусы, основной `RESPONSIBLE_ID`, дату закрытия, дату крайнего срока, перечень неактуальных поручений.
3. Уточнить признак «неактуально» по конкретным полям/БП; не вычислять ИД до этого.
4. Для расчёта ИД использовать правило: поручение выполнено при завершении главным ответственным, неактуальные не входят в знаменатель, но выводятся отдельно. Историческая дата комментария не подменяет дату фактического закрытия.
5. Отдельно включить сравнимые недельные срезы и динамику относительно прошлого месяца (нельзя вывести их из текущего одномоментного ответа).

```bash
python3 -m pytest -q tests/test_live_probe_v68.py
python3 -m compileall -q live_probe_v68.py probe_cli_v68.py
```

Для диагностики не требуется перезапуск `bitrix-dashboards`. Веб-страницы v6.7 продолжают работать. Никаких файлов `main.py`, переменных токенов, реальных SQLite или конфигурации systemd в репозитории нет.

## Ошибка при запуске CLI на gsprom-app113 (24.11.2026)

Проверено на серверном скриншоте: архив извлечён, CLI запускается, но старый диагностический клиент выводит `{"ok": false, "error": "Ошибка интеграции; проверьте журнал на сервере"}`. При этом команда была запущена от `root` с **примерным** `--group-id 123`. Это **не доказывает** отказ REST или недостаток прав: общее исключение может возникнуть ещё при импорте `tools.tools`.

Безопасная первая проверка, без REST-запроса и раскрытия секретов:

```bash
cd /webapp/app
sudo -u dev env PYTHONDONTWRITEBYTECODE=1 python3 -B - <<'PY'
import sys
sys.path.insert(0, '/webapp/app')
try:
    from tools.tools import fast_bitrix
except Exception as exc:
    print('client_import=ERROR', type(exc).__name__)
else:
    print('client_import=OK', 'callable='+str(callable(fast_bitrix)))
PY
```

Следующий шаг – выполнить диагностику от `dev` с **реальным и явно разрешённым** ID пилотной группы, заменив `123` в обеих позициях. В коде `probe_cli_v68.py` теперь отдельно распознаются ошибки загрузки клиента, а в `live_probe_v68.py` – тип ошибки REST, без вывода текста исключения (который может содержать конфиденциальные сведения). Изменение кода не затрагивает сервер, пока туда не перенесена новая версия файлов. Повторная установка v6.7 или рестарт общей службы не требуются.
