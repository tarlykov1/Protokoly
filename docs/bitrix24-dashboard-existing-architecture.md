## Паттерн для кабинета контролёра

1. Точка входа — PHP-страница в каталоге корня Битрикс24, как `/memo-activity/`; не требуется локальное Bitrix-приложение.
2. В браузер не выводить backend-токены; запросы идут через PHP `api.php` после `prolog_before.php` и `$USER->IsAuthorized()`.
3. PHP-бэкенд должен проверять право пользователя на **конкретные группы**: одного `IsAuthorized()` недостаточно. Пример явных ролей и членства — архив 2 (`UserToGroupTable`).
4. FastAPI должен доверять `X-Bitrix-User` **только при одновременном подтверждении серверного секрета**, с ограничением сетевого доступа к backend. Передавать ID из URL/браузера нельзя.
5. Для нескольких групп фильтровать результаты по правам конкретного пользователя на сервере, до отправки JSON; не выдавать полный кэш МЕМО всем авторизованным.
6. Для изменения данных/принудительной выгрузки — POST, `check_bitrix_sessid()`, отдельное разрешение.
7. Не менять действующие PHP-точки входа и стабильный МЕМО без отдельного тестирования.

## Важные замечания

- В архиве 3 `README.txt` прямо указано: **старый iframe в МЕМО больше не используется**, используется PHP-прокси. Это исправляет прежнее ошибочное предположение.
- Копии кэшей `portfolio_data.php`, `dashboard_it_data.php`, `*.lock` и вложенные ZIP-версии не должны автоматически попадать в исходный код Git.
- В архиве 4 `config.php` находился серверный секрет. **Никогда не загружать исходную конфигурацию с секретом в Git**, хранить его вне репозитория; для опубликованной копии заменить на заглушку/чтение окружения. Секрет, если он где-либо раскрывался вне доверенной среды, нужно ротировать.
- Важно сверять с работающим сервером: сохранённые снапшоты описывают состояние на дату выгрузки, не являются командой автоматического развёртывания.
